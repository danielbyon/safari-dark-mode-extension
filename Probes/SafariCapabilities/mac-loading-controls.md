# Mac Safari loading and marker experiment

Use these controls before resuming the rendering and lifecycle matrix. The browser observations from the first run have their own [package fingerprints and fixture receipts](../../docs/evidence/safari-capabilities/mac-safari-27.2/observations.jsonl). The steps below exercise different probe code.

## 1. Prepare independent installations

1. Build from the reviewed commit using the lockfile and the [build instructions](README.md). Run `npm run build`, `npm run build:ordered`, `npm run package` and `npm run package:ordered`. The staged resource sets are in `.build/<variant>/extension`. Record `resources.sha256.json` beside each directory. If the fixture origins change, build again and record the new hashes.
2. Obtain owner authorization for the shipping Mac, disposable profile, temporary extension, fixture server and fixture-only permission changes. Record the starting unsigned-extension setting. Start the server using the same origins used to build the package. Record the actual served HTML, page script and stylesheet digests and check the ordinary and strict response headers.
3. Use a fresh profile and independent temporary installation for each manifest comparison. Record the variant, fresh storage state and absence of preexisting grants. Never reload a different variant into the same temporary slot for an independent comparison. In the previous run Safari initially selected Personal, and cycling the mixed global switch temporarily selected all profiles while site grants were empty. Inspect the individual profile switches before granting anything. If another profile is active, stop with grants empty and have the owner establish lab-only activation. Use only the lab window for the run.
4. Keep full snapshots local. The popup export is available after the background confirms a regular profile. It keeps ordered observations, grant roles, stage names, error classes and computed effects. Exclude identifying URLs, private extension origins, port or browser identifiers and unrelated tabs from shared evidence.

## 2. Marker and strict-CSP controls

1. Use an ordinary light fixture (`?theme=light`) and the matching strict fixture (`?theme=light&csp=strict`). Keep variant, host, fixture bytes, palette and site action the same. Before enabling the extension, record each fixture's `policyRequest`, active site `themeRule`, `root` foreground/background and resource swatch. Verify only the strict response supplies the strict header. Repeat the negative control with the probe paused.
2. Acquire the top-host Deny/Allow calibration in the lab profile. Start a fresh document after calibration. Enable the marker with valid access, saved activation On and the same appearance in both pages. Record `marker-inserted`, then `marker-root-style` with its before, expected and after foreground and background. Run the same fixture observation after styles settle. Pause and repeat the fixture observation for restoration.
3. An `applied` result requires both target colors and a change from the previous pair. `already-matched` needs a distinct positive control. If only the ordinary page changes, record the difference and both responsive controls. Attribute a CSP restriction only when the matched controls and policy evidence support it. A missing site rule, a failed ordinary control, or disagreement between the extension and the settled fixture leaves attribution open.

## 3. Diagnose the dynamic package

1. On a fresh eligible ordinary page, select the candidate. Check the first-party module's URL resolution, requested import, fulfilled import, completed evaluation and same-world signal. The control and UMD imports proceed independently, so a stalled control leaves the UMD outcome observable. Repeat on a fresh strict page. A resolved resource URL proves only that the extension could construct it.
2. For the audited UMD, inspect the before-import send, receiver and echo, then the URL, import, evaluation, isolated-world global, public API and registration events. A rejected import can hide the difference between access failure and an exception before the first observable statement. Record the error class and the last observable stage. A fresh UMD global after rejection provides evidence that evaluation began. A preexisting global makes that document unsuitable for a fresh import comparison.
3. Record the after-import message separately from the public enable attempt and `candidate-enabled` result. Disable the candidate in the same document. Require `candidate-disabled` with `enabled: false` to credit a successful public disable. For all three messaging phases compare caller return kind, background receipt and echoed reply. An absent caller promise leaves the reply unavailable even if the receiver ran.
4. Stop dependent candidate rendering, resource and teardown cases at the first missing prerequisite. A failed first-party control narrows the question to the shared loading path. A successful control followed by a UMD rejection calls for the UMD-specific trace. Neither result alone identifies Safari's resource-access policy.

The dynamic package contains both files, verifies their bytes in the installed wrapper layout, resolves them with `runtime.getURL`, and imports them from the isolated content world. Neither manifest declares web-accessible resources. MV2 declarations identify exposed files. MV3 also scopes exposure to sites or extensions. Declaring a file changes who may fetch it. Manifest-declared content scripts follow their own injection rules. Safari access to these private dynamic imports remains a browser experiment. [Mozilla manifest reference](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/web_accessible_resources) · [Chrome resource access](https://developer.chrome.com/docs/extensions/reference/manifest/web-accessible-resources) · [Content script ordering](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_scripts)

## 4. Compare manifest order

Run `npm run compare:ordered` for the [offline manifest and three-phase controls](tests/ordered-umd/README.md). It executes the unchanged classic UMD between two first-party scripts in a fresh synthetic realm. With activation On, the public API enabled and disabled the fallback style. The receiver got one send at each phase. The caller got an echoed promise before evaluation and `undefined` after evaluation and after disable. With activation Off, evaluation still registered the API and changed messaging before any eligibility decision could run. [Original measurements](../../docs/evidence/safari-capabilities/loading-controls/ordered-comparison.json)

A declarative list cannot await the exact-origin and grant checks between files. Its host matches also span ports. The separately packaged browser preflight therefore declares only an inert exact-origin marker before the content entry. On a current eligible decision it samples the ordinary send and records `blocked-eager-umd`. Its baseline occurs after the decision. The offline list samples before its middle script at document start. The post-evaluation and post-disable phases for the actual ordered UMD remain unmeasured on shipping Safari.

## 5. Restore

Remove each temporary installation and fixture grant, close the lab window, remove the disposable profile and restore the initial unsigned-extension setting. Stop the fixture server started for this run and verify its ports have closed. Record any incomplete restoration. Retain the independent receipts before comparing variants.
