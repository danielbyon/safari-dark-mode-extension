# Ordered UMD comparison

Run `npm run compare:ordered` from the probe directory. The command prints two JSON records, each from a fresh Node VM realm. The runner uses this directory's manifest to select the three classic scripts in order. It reads `darkreader.js` directly from the pinned npm package and checks its SHA-256 before evaluation. The browser packager only reads the manifests in `extension/`.

Both runs assume a fixture site grant. The first simulates activation on. Its document has a root and no head, as can happen at document start. The real public `enable()` sets `isEnabled()` and inserts a fallback stylesheet with CSS text. Calling the real `disable()` clears the flag and removes that node. The synthetic document has no CSS engine to measure the resulting appearance.

The before script calls the ordinary messaging API in the content world. The synthetic receiver echoes the caller's ID and phase. After the UMD runs and again after disable, the receiver still gets one call with the matching ID and phase. In both cases the caller gets `undefined`. Before evaluation it gets a promise and the echoed reply. The runner records the caller and receiver separately so a missing reply cannot be mistaken for a dropped send.

The second run sets fixture activation off. The UMD still exports its public API and changes what the caller receives from the ordinary message. The after script skips enable and disable. A site grant and a URL match let a browser dispatch a declarative script list. The manifest cannot use the probe's asynchronous eligibility decision to skip its middle file.

The separately built `ordered-preflight` browser wrapper therefore declares only its inert preflight followed by the ordinary content entry. Its preflight marker appears before the eligibility decision. An eligible candidate request records the ordinary baseline and the eager-UMD incompatibility. Loading the unchanged UMD by a programmatic file injection after a decision would have different timing. It would require proof that the target document and eligibility are still current at evaluation on each tested Safari build.

Both browser variants package `packaged-control.mjs` and the unchanged UMD inside the extension. Neither manifest declares web-accessible resources. The dynamic loader resolves each asset with `runtime.getURL` and imports it from the content world. A fulfilled control import whose export matches `globalThis` establishes loading and evaluation of that file in that world. A rejected UMD import can identify partial evaluation if the pinned UMD created its global before it failed. Without that evidence the rejection leaves loading, parsing and evaluation unresolved. These results alone cannot establish which resource declaration Safari requires.
