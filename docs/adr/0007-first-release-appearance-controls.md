# Full appearance controls are a first-release requirement

The owner selected the expanded appearance controls for the initial release because the product must compete at launch. Presets-only and a reduced customization launch were rejected. This increases the combinations that rendering evaluation and usability validation must cover; it does not relax the existing compatibility and performance priorities.

## Accepted scope

1. Adaptive appearance, polished palette presets, and custom background, text, and link colors.
2. Brightness, contrast, saturation, color warmth, and required v1 image-dimming control (defaults off). Page-color adjustments must not inadvertently transform preserved visual content; image dimming affects content images, including reliably identified CSS background images, not icons or video. Media classification and coverage follow ADR 0006.
3. The selected theme supplies the reusable base; independently inherited appearance overrides apply afterward (ADR 0002). Preserve content images and other visual media by default unless the user deliberately chooses an applicable adjustment.
4. Keep ordinary use understandable for nontechnical users. Show appearance selection and preview simply, with detailed controls behind an editing or advanced action. Exact ranges, color-space behavior, and control interactions require engine evaluation and interface design.
5. Custom time schedules ship in v1. Apple Shortcuts integration is in product scope but deferred to v2. Include macOS keyboard shortcuts for temporarily toggling darkening in the current tab and pausing or resuming darkening. The tab toggle does not modify saved site rules; its lifetime is defined in ADR 0002. Theme import, export, and sharing are explicitly out of scope; theme creation and editing and opt-in personal iCloud sync remain in scope.

6. Provide an unsaved live appearance preview bound to the current page/document and editing context. Evaluate explicitly edited fields and override removals as hypothetical changes at the selected editing scope against the latest saved configuration; normal inheritance and narrower overrides apply (ADR 0002, Q79). Use Default previews removal at the override's owning scope, not substitution into the final appearance. Incorporate newer saved changes when resolving the draft. Editor dismissal, reload, any new top-level document, or any observed top-level URL change (including same-host path, query, fragment, anchor, and SPA navigation) discards the preview and resolves the latest saved configuration, not a frozen snapshot. Ordinary DOM changes without navigation retain the preview. Query and fragment remain irrelevant to persistent rule matching; preview invalidation is a separate concern (Q81). Changing save scope retains explicitly edited fields but recomputes/displays their effect at the new scope, including narrower overrides. Explain why a narrower override prevents a visible change and allow scope selection. Save commits only the edited fields or explicit override removals at the selected scope or as defaults, discards the draft, and resolves actual saved appearance; explain any difference after Save as Default when the global save target differs from the preview scope or site overrides remain. Explicit live preview may bypass ordinary activation/native-dark preservation, never Safari authorization, valid purchase access or Pause Everywhere (ADR 0002). Keep preview lifetime distinct from temporary tab activation.
7. Built-in themes are immutable and cannot be deleted. Users may create, name, duplicate, edit, and delete custom themes. Saving edits to a built-in theme in the theme editor creates a custom theme with a precomputed proposed name (tentative example: `<theme name> - Customized`); final copy and duplicate-name handling remain open. This does not implicitly turn a website-only adjustment into a new shared theme. When deleting a referenced custom theme, explain the affected rules/defaults and let the user choose a replacement. Handle stale references and fallback without resurrection according to ADR 0003.
8. WCAG 2.2 Level AA is the accepted minimum accessibility target (Q78). Enforce applicable criteria for code, themes, and transformations controlled by this product. Every unmodified built-in theme must meet applicable appearance/contrast criteria, including generated adaptive output; an attributable failure in our code or themes is a release blocker. Users may deliberately override colors or other appearance settings even when the resulting appearance fails those requirements. Warn about poor contrast without blocking, clamping, or silently correcting explicit choices solely to meet contrast thresholds, and provide a guided route back to the unmodified built-in appearance. Identify relevant appearance overrides and their owning scopes; let the user explicitly remove them, explaining broader effects before changing a broader rule or global default. Selecting a built-in theme does not itself clear overrides, and no automatic scope-specific bypass or silent broader reset is introduced (ADR 0002, Q80). Narrow compatibility exceptions for broken rendering follow ADR 0009. Qualification and guarantees apply to what we control, not to preexisting third-party content, semantics, behavior, or inaccessible frames. The customization exception covers only the accessibility consequences attributable to deliberately selected appearance values. It does not exempt unrelated defects in our interface (including accessible recovery controls), preference resolution, renderer, media preservation, or preservation of website functionality. For example, intentionally low-contrast text is permitted, but unexpectedly unusable unrelated controls or transformed video remain product defects; an inaccessible recovery action is still a product defect. WCAG conformance is a property of a complete web page; do not claim that our extension makes arbitrary third-party websites conformant. Use controlled color roles, states, adaptive output, and rendered fixtures to qualify our appearance behavior in T6, with representative third-party cases to detect and attribute regressions introduced by our transformations. An external limitation does not excuse an accessibility regression caused by our code. Report external limitations separately from product-controlled failures. The native app and extension popup must support accessible labels, VoiceOver, keyboard navigation, and platform text sizing; specify slider value announcements, inherited-value explanations, focus order, resizing, and non-color-only cues in UI acceptance criteria.
9. Ship English at launch. Prepare all user-facing strings for localization in the native app and web extension; additional translations and multilingual UI qualification are not required for v1.

## Competitive evidence and limits

Dark Reader already advertises brightness, contrast, custom palettes, native-dark detection, and website settings. Apple's Noir editorial explicitly describes current-page settings and keyboard shortcuts. Noir's current release notes also describe additional advanced rendering controls.

These facts mean sliders and exact-page settings are competitive requirements, not sufficient evidence of superiority. The proposed differentiation is the complete domain/hostname/section/page model, understandable per-setting inheritance and defaults, and demonstrated rendering quality. The available product documentation does not establish that competitors lack every part of this model. Dark Reader's general extension help even documents path and regex patterns; its Safari-specific behavior and exact preference inheritance need direct comparison.

The owner's goal is to be competitive and better from launch. The exact comparison corpus, launch-quality thresholds, additional media-repair controls, and implementation feasibility on supported platforms remain decisions or research, not measured successes. The owner selected standalone Safari web-app support where available; theme sharing/import/export were rejected, not deferred to an assumed later release.
