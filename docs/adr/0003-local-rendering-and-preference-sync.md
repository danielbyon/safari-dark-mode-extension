# Local rendering with opt-in preference synchronization

The owner chose on-device rendering, no browsing-history collection or analytics, no required application account, and explicitly submitted reports. Optional iCloud synchronization shares the theme collection, persistent site rules, and global appearance defaults only after explicit opt-in. Default activation mode, schedule configuration, and Pause Everywhere remain device-local so an iPhone and a Mac can activate darkening independently. Persistent site-rule activation overrides synchronize with their site rules. Temporary tab overrides and unsaved previews never synchronize. A rule inheriting activation can therefore behave differently on each device; a synchronized Follow System override follows each device's own system appearance.

## Consequences

1. Local use does not require synchronization or an application account; the purchase-access rules still apply.
2. Synced site rules include user-saved website addresses. They are preferences rather than a record of browsing activity, and the opt-in explanation must make this distinction clear.
3. Save as Default changes the selected baseline theme and appearance values on participating devices when preference sync is enabled. It preserves site-rule overrides.
4. Keeping only the theme collection and site rules in sync while retaining device-specific appearance defaults was considered. The owner selected shared defaults so appearance customization follows the user consistently.
5. Family Sharing grants purchase access to other eligible Apple family members; it does not merge or publish their separate personal preferences.
6. A developer-operated browsing-data or analytics service was not selected because it conflicts with the accepted privacy direction.
7. Resolve sync conflicts automatically, with last edit winning for competing edits to the same setting; retain independent edits to different settings. A deletion must not be undone merely because a stale device reconnects; deliberate recreation is allowed. Do not present conflict-resolution UI. The exact ordering, deletion representation, and storage API remain implementation decisions; synchronization is not promised to be instantaneous.
8. Private Browsing uses existing preferences wherever Safari allows the extension. Visiting a private page never creates a saved rule. Unsaved adjustments remain temporary. An explicit Save for This Website or Save as Default persists normally, applies beyond Private Browsing, and participates in sync when enabled. Explain these consequences before the save; do not silently persist private-page visits or unsaved edits.
9. Theme import, export, and sharing are excluded. Opt-in preference sync is not a public theme-distribution feature.
10. Enabling sync merges local and iCloud preferences under the accepted last-edit-wins policy. Disabling sync retains the current local configuration. Re-enabling reconciles intervening changes. Switching Apple Accounts requires renewed consent before syncing preferences to the new account. Local editing and reading preferences must remain available through internet outages. Do not automatically send saved addresses to another account.
11. Report Appearance Problem is an explicitly authorized, user-reviewed support flow. Candidate report contents include the affected website address with query parameters and fragments removed, app/OS/Safari version where available, effective appearance settings, rendering method, bundled compatibility-configuration version, relevant non-sensitive diagnostic information, and an optional user-provided screenshot and description. Show the information before submission and allow the user to review it; do not automatically upload reports, browsing history, page content, cookies, or authentication information. A path or optional screenshot may still contain sensitive information, so the user must be able to review the content before choosing to share it. Use a prepopulated support email with optional user-authorized attachments, rather than a dedicated reporting backend. The user reviews the report and chooses whether to send it; public GitHub issues are not the product's customer support channel. Allow editing or removing sensitive report fields and canceling before sending. Specify a usable copy-to-email or attachment handoff fallback if email composition is unavailable, without a reporting backend or theme export feature. The support address and platform handoff details remain open.
12. Provide a distinct Delete iCloud Configuration action with explicit confirmation. It deletes the synchronized configuration, disables sync on the initiating device, and retains that device's local configuration. Ordinary Disable Sync retains both the local and cloud configuration. Other participating devices retain local preferences, including edits made offline before learning of deletion, but stop participating in the deleted configuration as soon as they learn of it. Stale copies or pending uploads must not recreate it. Creating or joining a new cloud configuration requires explicit user action. Do not report cloud deletion as successful until confirmed; distinguish pending/failed deletion and qualify retry and recovery behavior. T4 selects the mechanism and verifies deletion/reconnection semantics before committing to a store.
13. When deleting a referenced custom theme, record the user's chosen replacement as an observable outcome, including for later-arriving stale references to the deleted theme. If the chosen replacement remains valid, redirect the reference to it; otherwise follow a valid replacement or restore inheritance (or a valid built-in fallback for defaults that cannot inherit). Preserve unrelated appearance overrides. Never resurrect the deleted theme or expose dangling references or conflict-resolution UI. T4 must define deterministic fallback and replacement-chain behavior, including missing/cyclic references and concurrent edits, and verify these outcomes before the schema is frozen.
