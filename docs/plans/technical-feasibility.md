## Accepted product baseline

`CONTEXT.md` and ADRs 0001–0009 are the authoritative detailed decision records. This plan indexes the requirements that the investigations must preserve; it does not supersede them.

- Commercial Safari product for iPhone, iPad, and Mac with core feature parity at launch. Rendering quality, compatibility, performance, and accessible interaction are primary acceptance criteria, ahead of merely increasing feature count. Compare against Dark Reader and Noir; avoid claims of unique features or superiority without evidence.
- Three onboarding activation choices: Always On, Always Off, and Follow System. Schedule is an additional device-local default mode in settings. Support weekday selection, start-day overnight windows, start-inclusive/end-exclusive boundaries and current local wall time; prevent equal start/end selection. Recompute after clock/zone changes and suspension. Real-page rendering requires Safari permission and valid access; Pause Everywhere persists across restarts until explicit resume. Temporary tab activation overrides saved activation but does not override native-dark policy. An explicit live preview can bypass ordinary activation/native-dark preservation but not permission, access or pause. macOS shortcuts are scoped to Safari/supported web apps; tab overrides survive same-host navigation and reload, not cross-host navigation, tab closure, explicit restoration or duplication/session restoration.
- Domain, exact-hostname, section, and exact-page-path site rules, with one rule per scope and field-by-field inheritance across all matching sections in increasing specificity. Resolve the theme reference independently and apply inherited explicit appearance overrides to that base. Honor registrable-domain boundaries, including private suffixes. Ignore query/fragment and treat HTTP/HTTPS and port variants alike. Default save preserves exceptions; restore inheritance removes a local override. Website activation can explicitly follow system or inherit a scheduled default, but does not support a separate site schedule. Safari profiles share preferences.
- Adaptive appearance, palette presets, reusable custom themes, custom background/text/link colors, brightness, contrast, saturation, warmth, and independently controlled image dimming (required v1 control, off by default). Preserve content imagery and video by default; adapt interface graphics as necessary and preserve chart/semantic distinctions. Dimming applies to reliably identified content images, including CSS backgrounds, not icons or video. Respect native dark mode unless explicitly overridden. Preview evaluates hypothetical draft edits and override removals at the selected editing scope against the latest saved configuration; narrower overrides still apply. Changing save scope retains edited fields and recomputes their effect. Dismissal, reload, a new top-level document, or an observed top-level URL change including query/fragment/anchor/SPA navigation discards the draft; ordinary DOM updates retain it. Saving removes the preview and resolves actual saved behavior. An eligible preview's rendering permission is separate from appearance resolution. Preserve the two explicit scope/default saves. Our code and immutable built-ins must meet applicable WCAG 2.2 AA requirements, including generated adaptive appearance; users may freely customize even below those thresholds, with non-blocking warnings and guided recovery of the unmodified built-in by explicitly removing appearance overrides at their owning scopes, explaining broader effects and revealing inherited overrides. Ordinary theme selection does not clear overrides; no scoped bypass or silent reset. Editing built-ins in the theme library creates named custom copies. Qualification and guarantees apply to product-controlled behavior. Do not promise full conformance of third-party pages or count preexisting external defects as product failures; identify and address accessibility regressions introduced by our code. The customization exception covers only accessibility consequences attributable to deliberately selected values, not unrelated defects in the interface, resolver, rendering, media preservation, or website functionality.
- Authorized ordinary websites and web applications, dynamic navigation, and Safari Add to Dock web apps where supported. Authorized frames use the top-level website's configuration, with independent permission checks and native-dark preservation; embedded hosts' own saved rules apply when visited at top level. Safari-owned UI is excluded. PDF/document recoloring remains separate research, not a v1 requirement. Element-picking and arbitrary user CSS are not initial-release requirements; keep a recovery/reporting route. A second rendering method ships only if evidence demonstrates meaningful additional compatibility.
- Native Swift/SwiftUI app using Point-Free TCA, shared TypeScript/HTML/CSS Safari Web Extension, narrow versioned App Group/native messaging contract. The popup serves everyday browsing interactions; the containing app handles comprehensive settings, onboarding, commerce, and theme management. Exact implementation choices require feasibility evidence. English at launch; prepare localization in both surfaces.
- StoreKit-only commerce: seven-day subscription introductory offer when eligible, annual Individual ($1.99 US target), annual Family ($3.99), permanent Family Sharing-capable unlock ($6.99) covering future features within this app. Same app features for each route across supported iPhone, iPad and Mac versions, via universal purchase and a shared catalog. Use StoreKit localized prices and verified access; recheck target prices before launch. No custom licensing server or purchasing/verification infrastructure. Configuration and native sample preview remain available without active access; actual website transformation and live preview require valid access. Distinguish unknown/refreshing from confirmed inactive access, retain valid previously verified access, restore pages as soon as supported when access ends, preserve preferences, and respect Apple's intended paid-renewal grace policy. Commerce in the containing app, not the extension.
- On-device rendering, no automatic telemetry/browsing-history collection, no required application account for customers. Opt-in iCloud sync of theme collection, persistent site rules (including activation overrides), and global appearance defaults. Default activation mode, schedule configuration, and Pause Everywhere are device-local; previews and temporary tab overrides never synchronize. Last edit wins per setting; retain independent edits; no user conflict UI. Cloud-configuration deletion ends participation while preserving every device's local preferences and offline edits; require explicit action to start/join a new configuration and confirm actual deletion before reporting success. Prevent stale resurrection; redirect stale deleted-theme references to the valid chosen replacement or defined inheritance/built-in fallback, preserving other appearance overrides. Local editing works offline. Private Browsing visits and unsaved changes do not create persisted rules; deliberate saves disclose persistence/sync effects. Reviewed support email, optional attachments, no reporting backend.
- Bundled compatibility configuration for v1, with narrowly scoped diagnosable rendering exceptions to preserve usability, consuming the complete rendering eligibility decision (including eligible explicit previews), never independently granting eligibility or rewriting saved preferences; do not override deliberate low contrast merely for WCAG. Include configuration version in reviewed reports. Future investigation of declarative remote configuration only; no remote executable rendering algorithms. Theme sharing/import/export and outside contributions are excluded. Apple Shortcuts is deferred to v2. Profile-specific settings may be reconsidered based on customer demand.
- Public source under PolyForm Noncommercial 1.0.0 solely for GitHub Actions compute benefits, with earlier MIT grants preserved. Verify actual dependency licenses for commercial use and notices. Support the oldest major OS on each platform meeting the mandatory requirements; newer optional integrations must not raise the ordinary browsing minimum unnecessarily.

## Investigation principles

1. Resolve the largest technical risks first. A feasibility probe is deliberately narrow, disposable, and not a commitment to production architecture or code.
2. Use upstream documentation, source, actual version/license information, and small repeatable experiments. Distinguish documented availability, observed behavior, inference, and not-run cases. A simulator or generic browser result is not physical Safari qualification.
3. Use deterministic local webpage fixtures for repeatability and a small representative live-site subset for early triage. Do not build a framework to test Safari itself. Use real Safari and physical devices for cases that cannot be established more cheaply. Use a single extension probe where practical instead of creating separate throwaway application stacks for each question.
4. Preserve a compact decision record containing exact candidate revisions, environment, method, results, limitations, rejected options, and residual uncertainty. Do not retain personal browsing content, private credentials, or unnecessary device data in the public repo. Distinguish intentionally maintained regression fixtures/evidence from disposable build or qualification caches.
5. No production feature implementation, App Store Connect changes, account creation, signing/capability changes, external contribution workflow, new hosted services, or unapproved dependency/architecture commitment in this planning phase. Obtain approval for the individual investigation scope and any physical or account-dependent operation. Use the established serial development workflow; pin the eligible qualified immutable development-process release when an actual task is selected, not for this unstarted plan.

## Investigation contracts

### T1a/T1b — Rendering candidate audit and comparison

**Question:** Can a commercially usable dynamic rendering component meet the agreed appearance and compatibility requirements without an expensive permanent fork or an independently built renderer?

- Inspect the actual Dark Reader upstream source, reusable API, package/dependency licenses and notices, native-dark detection, site-fix mechanisms, supported color controls and media handling, build/bundle constraints, and Safari-specific extension features. Separate what the public API provides from internal extension-only behavior and features of the commercial Safari app. Pin candidate identity before measurements. Screen engine/runtime dependencies, bundle constraints and likely Safari/OS floors before recommending reuse. Identify support for the accepted built-in appearance accessibility requirement, independent appearance overrides, classified media treatment and bounded compatibility fixes; do not assume engine-specific capabilities meet the product contract.
- T1a delivers a small deterministic fixture/site subset, initial failure classification, reproducible measurement protocol (platform, viewport, theme/controls, page state, cache/network conditions, comparator versions/settings), and initial acceptance questions before T2/T1b measurements.
- Build the smallest experiment required to exercise enable/disable, dynamic DOM and stylesheet changes, palette controls, brightness/contrast/saturation/warmth, image preservation/dimming, and reversibility on Safari. Distinguish unsupported controls from controls that can be implemented by a small adapter without changing the engine. Test native-dark positives and false positives, inline styles, cross-origin styles/frames where authorized, CSS variables, SVG, shadow DOM, media, and representative dynamic content. Exercise top-level configuration across authorized frames, independent frame permission and native-dark preservation, dynamic native-dark transitions (including repeated native-dark detection after extension-generated darkening without self-detection or oscillation, then a website-controlled dark transition), readability of semantic states and interface graphics, preservation of photographs/artwork/video, required content-image dimming defaulting off, and bounded compatibility exceptions that never change saved choices or override eligibility. Include a fixture where an eligible explicit preview of an otherwise inactive page receives a required bundled fix and an ineligible preview cannot render. Compare generated built-in appearance against applicable WCAG 2.2 AA criteria. Distinguish defects in controlled code/themes/transformations from preexisting external limitations and consequences directly attributable to deliberately selected appearance values; customized appearance does not excuse unrelated defects.
- Compare identical page states with extension off, Dark Reader, Noir, and the candidate where available. Use the same viewport, OS/Safari, page state, permissions and equivalent theme settings. Record competitor versions/settings and deviations; a commercial competitor unavailable on a device is NOT_RUN, not a pass or a loss.
- Inspect light-flash/injection behavior and repeated enable/disable/navigation, visible page breakage and resource costs. Investigate filter/static alternatives only for reproducible unresolved failures. Avoid assuming filters are inherently cheaper or better.
- **T1a exit:** candidate source/license/API/OS evidence matrix, unknowns, and the preliminary protocol and exact requirements T2/T1b must test. Do not select an engine at this stage.
- **T1b exit:** measured per-requirement evidence matrix, important failures and severity, smallest required adaptation, estimated maintenance implications, and a justified engine recommendation (reuse/modify/replace). No selection on feature-list claims alone. If none meets the required bar, return a bounded next investigation or owner decision rather than silently relaxing the requirements.

### T2 — Safari capability and lifecycle probe

**Question:** Can Safari expose enough reliable behavior on each target platform to deliver the accepted interaction model?

- Establish an API availability matrix from Apple documentation and the shipping SDK/toolchain; consider supported manifest choices and their lifecycle tradeoffs. Verify content script injection at the earliest supported time, background suspension and wakeup, SPA route changes, same-host and cross-host navigation, tab closure, cross-origin and nested frames with permission, extension-popup open/dismiss, selective grants and revocation, Private Browsing, system appearance and local schedule refresh, and Add to Dock web apps where supported. Test permission/access/paused precedence, frame authorization, dynamic native-dark changes, eligible explicit preview bypassing ordinary activation/native-dark policy, discard on editor dismissal, reload, any new top-level document, or any observed top-level URL change (including query, fragment/anchor, and SPA navigation), retention through ordinary DOM changes without navigation, and latest-saved-state restoration. Do not infer whether content has meaningfully changed; verify observable navigation event coverage and record Safari limitations. Test a repeated native-dark check after extension-generated darkening, then an independent website-controlled transition, and eligible preview compatibility-fix application without bypassing permission/access/pause. Exercise tab override survival across same-host reload/back-forward/suspension, expiry across cross-host navigation/closure, absence on duplicate/restored tabs, app-scoped keyboard shortcuts, and pause persistence. Screen mandatory API availability and candidate minimum OS versions early.
- Check whether page appearance can be restored after disable, revocation, and discarded preview. Verify that stale work from a previous page or tab does not apply to a new navigation. Record limits for browser-owned surfaces and inaccessible content, not a promise to bypass them. If permission revocation prevents immediate restoration, identify an actionable recovery instruction. Verify schedule boundary cases (weekday start-day, overnight, start inclusive/end exclusive, DST skipped/repeated wall times, time-zone/clock changes, suspension/resume) and prevent equal times in UI; distinguish behavior that requires native integration or qualification later.
- **Exit:** minimal Safari probe with observed supported/limited/unavailable/not-run capabilities, reproduction steps, impact on requirements and candidate OS floors, and clear next decisions. Required Safari behavior not demonstrated remains unqualified.

### T3 — Native/extension boundary and local preferences

**Question:** What is the smallest reliable native/browser contract with one authoritative saved configuration?

- Evaluate maintained Apple-supported storage and native messaging options and compatible TCA/Swift versions. Specify one owner for persisted preference mutations, a versioned contract, revision/ordering and error behavior, and the read/refresh mechanism available when the containing app or browser process is not continuously running. Do not depend on direct native-to-JavaScript push without evidence. Screen TCA/compiler/storage/bridge deployment floors early.
- Exercise updates from popup and app, concurrent or stale writes, interrupted writes, extension relaunch, and schema evolution. Keep theme identity, per-setting inheritance, effective settings, unsaved preview, and temporary tab overrides distinct. Ensure the public-facing rule resolver has deterministic input and output; avoid duplicating divergent rule logic across languages. Prove theme-reference resolution independently of per-field appearance overrides, all matching section contributions, deletion/replacement fallback interfaces, and scope-aware preview: hypothetical changes and override removals at their selected/owning scopes against latest saved configuration, preserving narrower overrides; hostname blue and page green with a draft hostname yellow still previews green and explains the page rule. Include unrelated sync change while editing, scope retarget with draft fields retained, Use Default removal, discard and save against latest state, and Save as Default at a different target with narrower overrides. Verify guided built-in recovery reveals all applicable override sources, removes only explicitly selected overrides at their owning scopes, explains broader effects, and does not claim an unmodified result while overrides remain.
- Deliver a table of input URLs, stored scope identities, matching and nonmatching examples before persistence format is frozen. Cover /docs vs /docs/ vs /docs-old, repeated slashes, case, encoded separators and other percent encodings, IDNs and trailing-dot hosts, IP/localhost/non-registrable hosts, HTTP/HTTPS/port variants, PSL changes, invalid migrated/synced identities, query/fragment handling, and nested sections contributing independent fields. Preserve scope boundaries, exact path distinctions absent justified normalization, and exact-host behavior without inventing a registrable domain.
- Define the narrow entitlement result contract for T5 without inventing independent verification. Ensure saved configuration stays available when access expires.
- **Exit:** recommendation and evidence for authoritative storage/mutation ownership, native bridge/lifecycle behavior, version and compiler constraints, rule-resolution test cases, and remaining interface decisions. Exact schema is not approved by this plan.

### T4 — Optional iCloud sync

**Question:** Which Apple-supported option can satisfy per-setting merge and whole-configuration deletion without a custom service?

- Compare relevant Apple-native persistence/sync options and their limitations, including change observation, record/field granularity, quota, account changes, offline behavior, deletion semantics, and compatibility with the selected local/native extension architecture.
- Exercise two independent devices or controlled replica simulations for concurrent different-field edits, same-field conflict, clock skew/ties, reset-to-inheritance, rule deletion plus stale reconnect, custom theme deletion/replacement, opt-in merge, disabled sync, and renewed consent after account change.
- Explicit cloud deletion must retain local configuration including offline edits on initiating and other devices, terminate participation on other devices when deletion becomes known, prevent stale replicas/pending uploads from recreating the deleted configuration, and require explicit action to create/join a new one. Distinguish pending/failed deletion from confirmed cloud deletion. Evaluate a deletion generation/tombstone or supported equivalent, long-offline reconnect, partial failures and retry. Verify stale references to deleted Theme X resolve to chosen valid Theme Y or defined valid replacement/inheritance/built-in fallback without resurrecting X, including missing/cyclic replacements and concurrent edits; preserve unrelated overrides. Verify persistent site activation overrides synchronize while local default mode/schedule/pause and ephemeral state do not. Do not equate upload order with edit order without defining and testing semantics.
- **Exit:** selected candidate and conflict/deletion model with deterministic unit/integration scenarios and a bounded actual iCloud qualification plan. Record unproven guarantees and any owner decision if the accepted semantics cannot be achieved.

### T5 — StoreKit access

**Question:** Can StoreKit's verified transactions and subscription statuses supply a correct native access state to the extension throughout the lifecycle?

- Evaluate actual Apple-supported purchase APIs, product catalog, eligibility, restoration, Family Sharing and concurrent personal/shared access, non-consumable access, expiration, refunds/revocations, billing grace, offline continuity, and entitlement refresh when the app is absent or suspended. Investigate one universal-purchase app record/platform arrangement and shared catalog for all three purchase routes before establishing production App Store identities. Verify existing permanent/family-shared access is recognized before offering purchase. Distinguish unknown/refreshing/bridge failure from confirmed inactive, honor previously verified access within validity, and show that absence of valid access prevents actual website rendering/live preview but not configuration/sample preview/support/restore. Test invalidation of open pages at the earliest platform-supported opportunity. Prove a refresh path without routine app launches, or report platform constraints for owner adjudication.
- Use StoreKit local testing and sandbox where appropriate; distinguish simulated state-machine tests from actual Apple account/Family Sharing/renewal behavior requiring qualification. Use the accepted seven-day annual-plan trial and permanent purchase model. No own billing or verification backend.
- **Exit:** entitlement state/transition contract and evidence that valid access is respected, invalid access does not enable rendering, settings are retained, and renewal/plan transitions are represented correctly. Record what cannot be established without sandbox, physical devices, or App Store Connect configuration; do not modify those production settings during planning.

### T6 — Qualification method

**Question:** How will we demonstrate launch quality without an excessive qualification framework?

- Extend the preliminary T1a comparison protocol; preserve environment, page state, theme/controls, cache/network conditions and comparator version/settings provenance. Record evidence only for tests actually run.
- Final corpus: approximately 30–50 representative websites across content, commerce, forums, documentation, social, web apps, native-dark sites, forms, dynamic UI, media, SVG and frames. Include deterministic fixtures for regression and isolated edge cases, but do not substitute them for real website validation.
- Measure usability and visual breakage, contrast/readability, media fidelity, native-dark false positives/negatives, early light flashes, update/restore correctness, responsiveness, memory and sustained activity. Use exploratory baselines to calibrate repeatable sampling, severity classification and quantitative thresholds. Require independent gates for no known critical rendering regressions in approved scope, competitive rendering/resource targets against Dark Reader and Noir, and demonstrated scoped customization/inheritance/usability advantages. Do not average away critical failures. Qualify product-controlled code and every unmodified built-in theme against applicable WCAG 2.2 AA criteria, including controlled color roles/states, adaptive output and rendered fixtures; use representative website cases to detect regressions attributable to our transformations. Distinguish existing external limitations and accessibility consequences directly attributable to user-elected values from product-controlled defects. Include customized appearance cases: permitted intentionally low contrast, but no unrelated broken controls, unexpected changes to preserved video, or inaccessible recovery actions. Enforce qualification and guarantees only for what we control; do not claim full third-party page conformance or waive our own regressions on external pages. Obtain owner approval and freeze corpus, metrics, thresholds, and coverage before final candidate qualification; exploratory results are not a release pass. Do not move gates after observing final results.
- Favor pure resolver/activation tests, TCA reducer tests, adapter and local browser integration tests, then targeted real Safari and physical qualification where cheaper methods are insufficient. No arbitrary timeouts waiting for a person's actions; no unnecessary UI automation.
- **Exit:** approved comparison protocol and release acceptance criteria, with unqualified categories identified.

### T7 — Minimum OS determination

**Question:** What is the oldest major OS on each platform that can satisfy the required product behavior?

- Combine actual deployment constraints for Swift/TCA, StoreKit, Web Extensions and manifest APIs, App Groups/native messaging, iCloud sync, rendering requirements and browser lifecycle, and the supported build/distribution toolchain.
- Separate iPhone, iPad, and macOS results; use oldest feasible major versions, not an arbitrary cutoff. Validate actual Safari on candidate minimum versions, including representative older hardware where performance is relevant. Gate optional Add to Dock and other newer conveniences without silently dropping mandatory behavior.
- **Exit:** evidence-backed candidate deployment minimums and qualification gaps; get owner approval before setting deployment targets or dropping an agreed requirement.
